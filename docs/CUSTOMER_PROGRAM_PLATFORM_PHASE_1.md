# Customer and Program Platform — Phase 1 Evidence

Date: 2026-10-03  
Status: Passed  
Environment: Local Firebase Auth and Firestore emulators only  
Production impact: None; no rules, indexes, functions, data, or hosting were deployed

## Outcome

Phase 1 establishes the additive database and authorization foundation for TSA, Executive Signature (ES), and future programs without changing the existing TSA data authority. It defines exact document contracts, required indexes, server-only mutation boundaries, participant/staff access scopes, raw-response isolation, and executable regression tests.

Phase 2 may begin in emulator only. Production deployment remains separately locked by the implementation plan and tracker.

## Security results

The combined emulator run passed all of these suites:

1. `tests/member-account-rules.behavior.test.js`
2. `tests/organization-console-rules.behavior.test.js`
3. `tests/readiness-assessment-account.test.js`
4. `tests/customer-program-platform-rules.behavior.test.js`

Verified outcomes include:

- A signed-in participant can read only the canonical customer linked to their Auth UID and their own enrollments, entitlements, and attempts.
- Direct client writes to every new domain collection are denied; trusted server code owns mutations.
- Support can read customer identity and operational records but not raw ES responses.
- An ES program lead can read ES operations; raw-response access additionally requires `rawResponseAccess == true`.
- A privacy/data administrator or platform owner can read raw responses.
- An analyst can read aggregate records but not customer identity or raw responses.
- An organization representative can read only their organization's aggregate documents, not participant-level ES data.
- Published assessment definitions and versions are publicly readable; drafts remain restricted.
- Cross-customer and cross-tenant access attempts are denied.
- Existing TSA/member and organization behavior remains green.

## Query and size results

`firestore.indexes.json` declares the Phase 1 composite query shapes for customers, enrollments, entitlements, assessment attempts, consent events, duplicate candidates, audit events, and outbox events. Large/raw fields such as answers, payloads, and scoring inputs are excluded from indexing.

Representative serialized response payloads measured by the contract test:

| Payload | Measured size | Phase 1 ceiling | Result |
| --- | ---: | ---: | --- |
| Quick check | 67,187 bytes | 524,288 bytes | Pass |
| Full assessment | 68,487 bytes | 524,288 bytes | Pass |

The Phase 1 ceiling intentionally preserves at least 50% headroom below Firestore's 1 MiB document limit.

## Repository regression result

The full static suite result was 74 passed, 4 skipped because they require running emulators, and 1 known pre-existing typography failure. All four emulator-only suites passed in the combined emulator run above.

The remaining typography failure concerns the existing `.ra-data-rule` left border in the readiness-assessment prototype. It existed in the Phase 0 baseline, is unrelated to Phase 1 persistence/security files, and is not waived for a production release; it remains tracked as baseline work outside this phase.

## How to reproduce

Run the static contract:

```sh
node tests/customer-program-platform-contract.test.js
```

Run the complete security regression using isolated ports:

```sh
firebase emulators:exec --config firebase.phase1-emulator.json --only auth,firestore --project the-untaught-lessons "node tests/member-account-rules.behavior.test.js && node tests/organization-console-rules.behavior.test.js && node tests/readiness-assessment-account.test.js && node tests/customer-program-platform-rules.behavior.test.js"
```

Expected `PERMISSION_DENIED` emulator log entries are generated by negative security assertions. The gate passes only when the wrapper reports that the script exited successfully with code 0.

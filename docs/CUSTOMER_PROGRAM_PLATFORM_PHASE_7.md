# Phase 7 — Member Workspaces and Switcher

Last updated: 2026-10-04
Scope: entitlement-aware routing, the workspace switcher, and Account & programs, per the implementation plan's "Phase 7 — Entitlement-aware member workspaces" and the Phase 0 profile/workspace-menu and landing-order contracts
Status: in build, local/emulator only; begun ahead of Phase 6's formal pass (performance/accessibility evidence still outstanding there), mirroring the Phase 5 precedent of starting a phase's local/design work once the prior phase's product/security substance has passed and only production-dependent evidence remains open

## Outcome so far

Built and emulator-verified the two decision-free building blocks every other Phase 7 deliverable depends on: a self-service read of which workspaces a signed-in person is authorized to use, and the pure landing-order decision the Phase 0 contract already specifies. Neither is wired into the live member-facing pages yet, and neither has been deployed.

## Implemented controls

- `getMyWorkspaces` is self-service and read-only: any authenticated caller may ask about their own access, with no role requirement, and it never creates a customer, auth-link, or any other record as a side effect (unlike `resolveMyCustomerIdentity`, which is transactional-create-on-first-use by design).
- TSA eligibility is read directly from `authorized_members` (the authority during this project per the schema's "Authority during transition" table), not from the new `customers`/`enrollments` projection — consistent with TSA protection rule 10 ("TSA remains authoritative until shadow verification passes," which is Phase 8's job, not Phase 7's).
- That TSA read lives in the callable layer (`functions-admin/index.js`), never inside `functions-admin/customer-program-service.js`. A pre-existing Phase 2 static contract test (`tests/customer-program-phase2-contract.test.js`) asserts the cross-program service module must never reference `authorized_members`, to keep it structurally decoupled from legacy TSA code. The first draft of this function put the read inside that module and the existing test caught it immediately; it was moved to the callable layer and the suite passed clean on the next run.
- ES eligibility requires an `entitlements` row with `programId == "executive-signature"` and `status == "active"` for the caller's linked customer — a revoked, expired, refunded, pending, or consumed entitlement does not grant the workspace.
- The landing-order resolver (`assets/workspace-routing.js`) is a dependency-free, dual-use module (plain browser script via `window.UtlWorkspaceRouting`, or `require()`-able directly in Node for exhaustive testing) implementing the Phase 0 order exactly: authorized deep link, then last-visited-if-still-authorized, then the only workspace, then a chooser for 2+ with no history, then account/access-help for zero.

## Workspace switcher — first slice

The real member-facing shell is not `index.html`/`programs.html` (the public marketing site) but `member-login/content-config.js`, a single rendering module that already implements the profile menu, including a proven pattern for conditionally revealing a section based on an async access check: the existing "Organization" entry (`data-organization-access`, hidden by default, revealed by `hydrateOrganizationAccess()` calling `getMyOrganizationAccess()`, cached in `sessionStorage` for 5 minutes, left hidden on any error).

Cloned that exact pattern for Executive Signature rather than inventing a new mechanism:

- A new hidden "Workspaces" menu section (`data-es-workspace-access`) linking to `apps/readiness-assessment/index.html`.
- `hydrateEsWorkspaceAccess()`, called alongside the existing `hydrateOrganizationAccess()`, calls the new `getMyWorkspaces()` client wrapper and reveals the section only when the response includes an `executive-signature` workspace; any error or absence leaves it hidden.
- Verified: `node -c` syntax check passes, and the full static repository sweep (75 files) is unaffected beyond the one pre-existing typography failure.
- Verified inert for every real member today: production currently has zero ES entitlements (confirmed by Phase 6's reconciliation), and this function needs no Firestore rules (it calls the already-deployed `getMyWorkspaces` Cloud Function directly), so even if this file were pushed right now, no current member would see a visible change.

Not yet done: the "switch workspace" interaction itself (today there is at most one new entry to reveal, not a true switch between landed workspaces), and the reverse link from inside the ES preview back to the member shell.

## ES participant entry wired to entitlements

`apps/readiness-assessment/index.html` previously had no way to tell a signed-in returning participant apart from a brand-new anonymous visitor at its own entry point: the landing screen's only "you already started" state (`landingReturnActions`) was keyed off an in-browser `sessionStorage` attempt, which says nothing about a real completed result recorded earlier or on another device. Quick Check's free/open-entry rule (approved product decision 6, "treat Quick Check participants as free participants, not TSA members") is unchanged — nothing here adds an entitlement gate to entry. This closes the separate, narrower gap: a signed-in person who already holds a real completed result should be told so, not silently pointed at question one again.

- Added `getMyEsStatus` to `functions-admin/customer-program-service.js`, structurally identical in spirit to `getMyEsWorkspaceAccess` (self-service, read-only, ES-only, no TSA dependency, no side effects) and composing that function's customerId lookup rather than duplicating it. For each of `quick-check` and `full-assessment`, it reports whether an entitlement exists, its status, its usage counters (`attemptsCompleted`, `retakesAllowed`, `retakesUsed`), and — only when that entitlement's status is `active` or `consumed` — up to 5 of the customer's most recent completed `assessmentAttempts` for that assessment, trimmed to the safe summary fields only (`attemptId`, `assessmentId`, `completedAt`, `overallScore`, `areaScores`, `profileLabel`, `band`). The `responseParts` subcollection is never read. To avoid requiring any change to `firestore.indexes.json`, the attempt lookup uses equality-only filters (no compound `orderBy`) and sorts/trims the small result set in memory rather than asking Firestore for a composite index that does not already exist.
- Wired the callable the same way `getMyWorkspaces` is wired: `getMyEsStatusHandler` in `functions-admin/index.js` requires only `requireVerifiedCaller` (no role gate), wraps the service call, and is registered in `__customerProgramCallableTest`.
- Added a matching `getMyEsStatus()` client wrapper to `assets/firebase.js`, returning a safe all-empty default (both assessments reporting no entitlement, no attempt) when signed out, exported alongside `getMyWorkspaces`.
- On the entry page, added a small, additive notice (`#accountResultNote`) above the existing primary/return action rows. It stays hidden for every anonymous visitor and for any signed-in visitor with nothing completed yet. For a signed-in visitor with a real completed attempt, it names which assessment and when, and links to the already-existing `my-results/` page rather than trying to reconstruct the rich interactive result screen from summary fields alone (see the design note below). The check runs off the existing `ra:account-readiness` event that `apps/readiness-assessment/assets/site-nav.js` already dispatches after resolving sign-in state, so no new auth-state listener was added; any error or absence of status just leaves the notice hidden, never blocking the anonymous/sample-data flow underneath it.
- Design note on scope: `index.html`'s interactive result screens (`renderResult()`/`renderFullResult()` and the whole scoring/content pipeline behind them) are built to score and render a full in-browser answer set against the local `ITEMS`/`CONTENT`/`PROFILE_DEPTH` registries — they do not accept a bare `{overallScore, areaScores, profileLabel, band}` summary as input, and retrofitting them to do so would mean faking facet-level detail, famous-people matches, and written profile sections the summary alone cannot support. `my-results/index.html` already exists specifically to render a returning participant's real, already-persisted result (today from the compatibility `users.products.readinessAssessment` projection, which mirrors the canonical attempt's summary fields at write time per the Phase 3 persistence contract) and was left unchanged, since it already works correctly on real data and duplicating that rendering path off the new canonical read would add a second, parallel source of truth for the same screen rather than fix an identified gap. The new canonical `getMyEsStatus` read is used specifically at the entry point, where no such rendering already existed.
- TSA impact: none. The notice only appears inside `apps/readiness-assessment`, is driven entirely by ES entitlement/attempt data, and `apps/readiness-assessment` remains excluded from both GitHub Pages and Firebase Hosting (see `README-assessment.md`), so this has no live exposure regardless.

## Account page extended

The existing Account page (`member-login/account.html`, rendered by `renderAccount()`/`accountPageHtml()` in `content-config.js`) now also shows an Executive Signature program row when the signed-in person has that workspace: `renderAccount()` additionally calls `getMyWorkspaces()` (tolerating its failure with an empty default) and passes the result into `accountPageHtml(account, esWorkspaces)`; a new `accountEsProgramHtml()` helper renders the row only when an `executive-signature` workspace is present, linking to `apps/readiness-assessment/index.html`. Verified by extracting and executing the function directly with real inputs (has-ES, no-ES, and undefined cases), plus new static assertions in `tests/member-account-foundation.test.js`. This only reaches TSA members today, since `renderAccount()`'s entry gate (`getMemberAccount()`) requires an `authorized_members` row to load at all — a fully ES-only customer cannot open this page yet. Fixing that is a separate, larger change to the shared `requireMember()`/login-gate mechanics used by every page in `content-config.js`, not attempted here.

## Not yet built (remaining Phase 7 scope)

- The reciprocal workspace switcher inside `apps/readiness-assessment` pointing back to the TSA member shell (it currently has no link back to `member-login`).
- Letting a fully ES-only customer (no TSA access at all) reach the Account page or any member-shell page — today every page's entry gate assumes TSA membership. No real ES-only customers exist in production yet, so this has not blocked anything, but it is a real gap in "entitlement-aware member workspaces" as a general capability.
- Deterministic routing wired to an actual navigation entry point (today `resolveLandingWorkspace` is implemented and tested in isolation, but nothing calls it from a real page yet — there is at most one extra destination to reveal so far, not yet a true multi-workspace switch).
- Accessibility and responsive verification of whatever UI gets built (P0-12's accessibility contract: keyboard-complete, visible focus, 200% zoom, 375px/768px checks, focus restoration, stale-deep-link recovery).
- TSA regression confirmation once the switcher is wired into the existing member shell (it must appear only for TSA members who also hold other access, and must never alter the plain TSA-only experience).
- A Phase 7 gate review once the above is complete.

None of this has been pushed to `main` or deployed; it exists only in the local working tree, consistent with how every other phase's UI work was built before its own explicit deployment decision.
